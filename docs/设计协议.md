## 1. 世界与状态表示（规范形式）

一切判分以此规范形式为准。

### 1.1 对象

| 字段 | 取值 |
| --- | --- |
| `id` | 对象在交互中的标识（如 `a`）；问答与操作都用它指称对象，不携带属性信息 |
| `kind` | `cube` / `pyramid` / `ball` |
| `color` | `red` / `green` / `blue` / `yellow` / … |
| `size` | `big` / `small` |
| `pos` | 见下表 |

### 1.2 位置（互斥）

| 形式 | 含义 |
| --- | --- |
| `("table",)` | 在桌面上 |
| `("on", 宿主id)` | 直接放在某物体上 |
| `("hand",)` | 在手中 |

位置只有这三种形式。

### 1.3 关系

问句与判分使用下列关系：

| 关系 | 含义 |
| --- | --- |
| `on(a, b)` | `a` 直接放在 `b` 上 |
| `held(a)` | `a` 在手中 |
| `clear(a)` | `a` 之上没有任何物体（`pyramid` 恒为真） |
| `on_table(a)` | `a` 在桌面上 |
| `supported(a)` | `a` 由某物支撑，即不在桌面上、也不在手中 |

### 1.4 状态快照

```json
{
  "objects": [
    {"id": "g1", "kind": "cube", "color": "green", "size": "small",
     "pos": ["on", "r1"]},
    {"id": "r1", "kind": "cube", "color": "red", "size": "big",
     "pos": ["table"]}
  ],
  "hand": null
}
```

## 2. 对象描述语言（指称）

问句与操作都要引用物体。统一的引用形式：

```
描述 := 量词? 属性* 类型 关系*
```

| 成分 | 取值 | 例 |
| --- | --- | --- |
| 量词 | `the`（定指）/ `a`（不定）/ `all` / `every` / 数量 | the / a / all / two |
| 属性 | `color` / `size` | red / big |
| 类型 | `cube` / `pyramid` / `ball` / `thing` | cube |
| 关系 | `on X` / `on the table` | on the red cube |

**例**：`the big red cube on the green cube`、`all cubes on the table`、`a pyramid`。

### 2.1 唯一性要求

- **定指 `the`**：匹配集合**必须恰好 1 个**，否则该题为**无效题**（生成器须拒绝）。
- **不定 `a`**：匹配集合 ≥ 1 即可，答案可以是集合中任一（判分时按「是否存在」处理）。
- **全称 `all` / `every`**：作用于整个匹配集合。

> 这条是自动生成的硬性检查项：**定指描述必须唯一命中**。

## 3. 操作集 O0

### 3.1 三个操作，以及**代码里的**实际前置条件

下表以 `shrdlu/ops.py` 的 `check_*` 为准，这是**唯一**有约束力的说法。任何一条不满足即判非法，被测者的正确行为是**拒绝**（§3.3）。

| # | 操作 | 语义 | 实际前置条件 |
| --- | --- | --- | --- |
| 1 | `pick_up(x)` | 抓起 x | ① x 存在 ② x 不是 `table`/`world` ③ **手为空** ④ `clear(x)`（上方没有其它物体） |
| 2 | `put_down(x)` | 把 x 放回桌面 | ① x 存在 ② **x 正在手中** |
| 3 | `put_on(x, y)` | 把 x 直接放到 y 上 | ① x、y 都存在 ② x ≠ y ③ y 不是固定物 ④ **y 能支撑**（见 §3.2）⑤ 若 x 不在手中：手为空或手中就是 x，且 `pick_up(x)` 本身合法 ⑥ `clear(y)`，除非 x 本来就**直接**在 y 上 |
`put_on` **允许隐式抓取**：x 不在手中时先自动 `pick_up(x)`。理由：对齐原版（一条命令即可完成）。

### 3.2 可支撑性（`on` 的目标）

| 宿主 kind | 能否作为 `put_on` 的目标 | 说明 |
| --- | --- | --- |
| `cube` | 能 | |
| `pyramid` | 不能 | **尖顶不能支撑**：原版对 "Stack up two pyramids" 的回答就是 "I CAN'T" |
| `ball` | 不能 | |

**只有 `cube` 能支撑**（`world.SUPPORTING_KINDS = ("cube",)`）；`pyramid` 一行在更早的协议里写成"能"，那是错的。

**`on` 取「直接接触」**（对应原版澄清里的选项 1）：判分最不含糊，且原版对"任意在上方"是要反问澄清的。

> 那个「同一个 `on`，两个 API 两种意思」的陷阱也随之消失了：`add(on=…)` 与 `set_pos(("on", …))` 都只是"放在顶上"。

### 3.3 非法操作的处理

| 情形 | 处理 |
| --- | --- |
| **测试者下发的指令非法** | **被测者可以拒绝**：拒绝即为正确行为 |
| **被测者执行了非法操作** | 该操作**不生效**（相当于没执行），并**直接判定被测者不理解** |

**判不理解的理由**：若被测者的世界模型正确，它本应知道该操作非法而**拒绝**；它仍然去执行，说明**它对自己所处的状态判断错了**，即判「不理解」。

测试者收到 `action` 后照它执行：合法操作生效，非法操作不生效。这一条消息的来回到此为止，测试者另外**记录**下"被测者曾试图执行非法操作"这一事实，据此判分。

### 3.4 测试者实际会发出的指令英文

由 `commands.render_instruction()` 生成，**这三句就是全部**：

| 操作 | 英文 |
| --- | --- |
| `pick_up(x)` | `Pick up the red cube.` |
| `put_down(x)` | `Put down the red cube.` |
| `put_on(x, y)` | `Put the red cube on the blue cube.` |

被测者一侧的解析器（`shrdlu/testee/nlp.py`）接受的**动词与介词**：

| 接受的写法 | 说明 |
| --- | --- |
| `pick up X` | |
| `put down X` | |
| `put X on/onto Y` | `on` / `onto` 都行 |

**不接受的写法**（会解析失败，因此测试者也不生成）：

| 写法 | 状态 |
| --- | --- |
| `Put X on the table.` | 不接受：放回桌面只有 `Put down X.` 一种说法 |
| `Put X on top of Y.` | 不接受：介词只有 `on` / `onto` |
| `Put X in/into/inside Y.` | 不接受：位置形态只有 §1.2 那三种，没有"装进去" |
| `Put X next to / in front of / behind Y.` | 不接受：位置是关系，没有方向与相邻 |
| `Stack / Place / Move X ...` | 不接受：动词只有 `pick up` / `put down` / `put ... on`（`onto` 亦可） |
| 并列谓词（`Put X on Y and Z in W.`） | 不接受：一条指令一个操作 |

## 4. 问句集 P0

P0 = **5 种题型** × **3 种属性** / **4 种关系**。 **答句全部是封闭式的**（`yes/no`、一个属性词、一个数字），判分零歧义，不涉及自由文本比对。

### 4.1 题型（`generator.SHAPES`，也就是 `shrdlu.ini` 里 `shapes` 能填的值）

| 题型 | 问的是什么 | 英文表层 | 答句 |
| --- | --- | --- | --- |
| `attr` | 某个物体的一个属性 | `What color is X?` / `How big is X?` / `What shape is X?` | 颜色词 / `big`\|`small` / 形状词 |
| `rel` | 某个物体是否处于某关系 | `Is X on Y?` / `Is X on the table?` / `Is X clear?` / `Is X supported?` | `yes` / `no` |
| `count` | 满足描述的物体有几个 | `How many cubes are on the table?` | 数字 |
| `exists` | 存在满足描述的物体吗 | `Is there a red cube on the table?` | `yes` / `no` |
| `all` | 满足描述的物体**全都**处于某关系吗 | `Are all cubes on the table?` | `yes` / `no` |

### 4.2 属性（只有三种）

| 属性 | 取值 | 说明 |
| --- | --- | --- |
| `color` | 调色板里的颜色词 | 生成场景只用到 `red`/`green`/`blue`/`yellow`；解析器与判分认得 §4.5 的全部拼法 |
| `size` | `big` / `small` | |
| `kind` | `cube` / `pyramid` / `ball` | `block` 与 `cube` 同义 |

**不纳入 `material`（材质）。** 原版对话中未出现材质提问。

### 4.3 关系（只有四种）

| 关系 | 语义 | 英文表层 |
| --- | --- | --- |
| `on(a, b)` | a 直接接触地放在 b 上 | `Is a on b?` |
| `on_table(a)` | a 直接在桌面上 | `Is a on the table?` |
| `clear(a)` | a 上方没有其它物体 | `Is a clear?` |
| `supported(a)` | a 直接放在另一个物体上；在桌面上或在手中都不算 | `Is a supported?` |

关系**可以嵌在名词短语里**（`the cube on the red cube`），但出题器只出**无歧义**的句子（用解析器当判据）。

### 4.4 名词短语的构造（`Desc`）

```
[the|a|all] [size] [color] [kind] [关系]        例：the small red cube on the table
```

- 限定词由题型决定：`attr`/`rel` 用 `the`，`exists` 用 `a`，`count`/`all` 用复数无冠词；
- 三个属性都可省（`the cube`、`the ball on the red cube`）；
- 生成器保证**每个物体都能被唯一指称**（不会出现两个 `small red cube`）。

### 4.5 答词表（`shrdlu/env/answers.py`，判分侧）

| 类别 | 接受 |
| --- | --- |
| 布尔答句 | `yes` `y` `true` `t` `1` `yeah` `yep` / `no` `n` `false` `f` `0` `nope` |
| 数字 | `0`–`12` 及 `zero`…`twelve` |
| 颜色 | 全部颜色词，`gray`→`grey` |
| 大小 | `big` `large` `huge` `bigger` / `small` `little` `tiny` `smaller` |
| 形状 | `cube` `block` `square` `cubic` `cubical` / `pyramid` / `ball` `sphere` |

**`0` 与 `1` 既是布尔答句又是数字**，所以解释**取决于问句要的是哪一种**，绝不靠猜。空答、拒答、或词表以外的回答**一律计错**：协议要求必须表态。

> **【已知问题，待修】** `exists` 与一元关系组合时会生成**不合语法的英语**：`Is there a ball clear?` / `Is there a ball supported?`（一次测试中会出现若干句）。解析器可以往返，因此测试全部通过；但问题出在**英语**表层，而英语理解正是被测能力，真实模型很可能无法解析。两种改法：改表层（`Is there a clear ball?`，需要解析器支持形容词化的一元关系），或由出题器不再生成这一组合。

### 4.6 明确**不支持**的构造

| 不支持 | 备注 |
| --- | --- |
| `material`（材质）、`weight`、`owner` 等其它属性 | 属性只有颜色、大小、形状（§4.2） |
| `beside` / `near` / `left of` / `right of` / `in front of` / `behind` / `above` | 位置是关系（§1.2），只有 `on` / `on_table` / `clear` / `supported` 四种问法 |
| 并列谓词、复合介词、比较级（`bigger than`） | 解析器不支持 |
| 自由文本答句、反问、澄清 | 协议要求封闭式表态 |
| P1–P4 的其余问句（原版问句集里更花哨的部分） | 未纳入 |

## 5. 交互机制

交互分**两部分**：**问答**（测试者发 `question`，被测者回 `answer`）与**操作**（测试者发 `command`，被测者回 `action` 或 `refuse`）。两部分都以物 `id` 作为对象的唯一引用：线上出现的对象标识（`observe` 的状态、`action` 的 `args`）一律是 `id`；问句与指令则是自然语言描述，由被测者把它们对应到自己那份模型里的 `id` 上（§2、§3）。

### 5.1 【关键发现】谁解析、谁生成是不对称的

| 角色 | 需要**生成** | 需要**解析** |
| --- | --- | --- |
| **测试者** | 语义 → 自然语言（出题） | 仅解析**封闭式答句**（极易） |
| **被测者** | 封闭式答句 | **自然语言问句 → 语义**（真正的 NL 理解） |

**测试者不需要实现问句解析器。** 因为问句是测试者自己生成的，它天然知道语义；手工题则以「问句 + 附带语义」成对录入，也无需解析。

→ 这把测试者的实现成本**省去约一半**：它只需一个**生成器**（语义 → 表层），加上一个**答句归一器**。真正难的 NL 解析全在被测者一侧，而那正是被测能力。

### 5.2 问句表层形式

**协议语言：英文。**

| 决策 | 内容 |
| --- | --- |
| 语言 | **英文**（与原始 SHRDLU 一致，词库与句式可直接对齐） |
| 表层形式 | **受限自然语言**（由 §4 的模板生成），而非结构化查询 |

理由：如果问句是结构化的，就只测了世界推理，**没测语言理解**，而语言理解正是 SHRDLU 的本体。

### 5.3 答句规范（英文）

| 语义 | 可接受答句（归一后） |
| --- | --- |
| 真 | `yes` / `y` / `true` / `1` |
| 假 | `no` / `n` / `false` / `0` |
| 数字 | `4` / `four` |
| 颜色 | `red` / `green` / `blue` / …（`grey`≡`gray`） |
| 尺寸 | `big` / `large` / `small` / `little` |
| 形状 | `cube` / `pyramid` / `ball` |

**必须表态**：空答、拒答（`I don't know`）、含糊 → **计为答错**（防止以回避换取过关）。

### 5.4 指令通道

除问句外，测试者还会下发**指令**（即操作集 O0，见 §3）。

**下发方式：逐条下发、逐条响应。** 测试者发一条指令 → 被测者响应 → 测试者再发下一条。合法指令要求执行，非法指令可以拒绝（拒绝即为正确）；若被测者反而去执行非法操作，操作不生效，并**直接判被测者不理解**（见 §3.3）。

被测者**必须显式回报拒绝**，否则测试者无法区分「正确拒绝」与「没有响应」。

| 测试者的指令 | 被测者**执行** | 被测者**拒绝** |
| --- | --- | --- |
| **合法** | 正确 | **不理解**（该做未做） |
| **非法** | **不理解**（做了不该做的） | 正确 |

指令的英文形态（测试者只会发出这几种句式）见 §3.4。

### 5.5 消息与回复的配对

双方**一行一个 JSON 对象**。每种消息对应被测者一侧的一个入口，回复就是它的返回值：

```
测试者 → 被测者 : {"type":"observe",  "state": {...}}   # 只在测试开始时发一次；载荷见 §5.7
测试者 → 被测者 : {"type":"command",  "text":"Pick up the blue pyramid."}
测试者 → 被测者 : {"type":"question", "text":"Is the red cube clear?"}
被测者 → 测试者 : {"type":"action", "op":"put_on", "args":["a","b"]}
被测者 → 测试者 : {"type":"refuse", "reason":"..."}
被测者 → 测试者 : {"type":"answer", "text":"yes"}
```

| 测试者 → 被测者 | 被测者 → 测试者（返回值） |
| --- | --- |
| `observe` | **无**（不需要回复） |
| `question` | `answer` |
| `command` | `action` 或 `refuse` |

一次测试就是这三个入口被调用若干次，顺序与次数见 §5.6。消息**一问一答**：测试者发出，被测者回一条，测试者再发下一条；`action` 之后测试者就照那个调用执行，回信到此为止。面向开发者的展开见 `testee开发需求.md` §1.2。

### 5.6 一次测试 = 三段

一次测试依次走完三段，**走完为止，没有提前结束**（划分与理由见 `README.md` §4.2）：

| 段 | 测试者做什么 | 被测者做什么 | 判什么 |
| --- | --- | --- | --- |
| **第一步** | 只发**题库里的问句** | 回答 | 对**初始状态**的理解 |
| **第二步** | 逐条发指令 | 把操作 **API 的调用发给测试者**（照旧是 `action` 消息） | **每个操作之后**，剧本驱动的那份状态 ↔ 被测者的调用驱动的那份状态 |
| **第三步** | **再问一组问句** | 回答 | 模型**自身对状态变化**的理解 |

**两轮问句**：测试者在指令前后各问一轮，题目的答案会随状态变化，两轮答案放在一起才能把「没看懂交来的世界」（第一步就错）与「没跟上世界的变化」（第一步对、第三步错）分开。**两轮题目是否相同由测试者的题库设计决定**：现行做法是把**同一份题库问两遍**，但两轮也可以问不同的题，协议不作规定。带自动出题的场景里，**题目是对着指令之后的状态出的**，所以按当前实现有些题在第一步问不了（定指不到）；这类题在第一步**跳过、不计入分母**，记录里会标明是哪一段跳过的。

落到线上只需要两条：

- **两份世界状态都由测试者维护**：一份是 **世界的当前状态**（按指令实际执行），一份是 **被测者通过操作表现出的世界状态**（从世界的初始状态出发、按被测者发来的 `action` 演化），第二步的对拍与第三步的判分都用它。
- **第二步的对拍不需要扩展协议**：被测者不需要回报任何状态，也不要求它交出模型；它自己如何记录这份认识是它的实现自由（`testee开发需求.md` §2.3），要给自己画图就用它自己维护的状态渲染（世界信息只有测试开始时那一份，见 §5.7）。

### 5.7 初始观察

测试者在测试开始时把初始场景交给被测者：一条 `observe`，载荷见下。**整次测试的世界信息就这一份**：此后测试者发的是问句和指令，世界在指令之后变成什么样，由被测者从自己发出的调用推出来。

这是测试台的地基：一次测试考的是「跟踪 + 推理」，而观察只发生一次正是把两者分开的地方（一次测试考的正是「从调用推出状态」这件事）；若每一步都能重看，考的就退化成感知了。

载荷有两种，**由测试者决定给哪一种**，而且这个选择本身就是测试的一部分：

```json
{"type": "observe", "state": {"objects": [...], "hand": null}}
```

```json
{"type": "observe",
 "image": {"format": "png", "scale": 2.0, "data": "<base64 的 PNG 字节>"}}
```

同一条 `observe` 里也可以两种载荷都给，但**要看的被测者必须拒绝这种消息**：它要的是一条只有图的 `observe`，否则回答里分不清哪部分是看来的、哪部分是读来的。

**谁决定给哪一种**：`--observe state|image`，默认取自 `shrdlu.ini` 的 `observe` （见 `README-env.md` 的配置一节）。给 `image` 需要 Pillow（要栅格化成 PNG）； `state` 与其余一切仍然零依赖。

### 5.8 图必须表达的信息（`image` 载荷的契约）

图必须让被测者认得出每个物体的：**id（画在物体上的那个字母）、形状、颜色、大小，以及它直接放在谁上面**。位置形态只有 §1.2 那三种，所以图要表达的正是"在桌面上"与 "直接放在谁上面"两项。

**唯一表达不了的是"在手中"**：它在图上是一个"左侧托盘"，靠虚线框和标注才认得出，是整张图里最弱的一处。因此遇到含"在手中"的场景，测试者**拒绝发图并报错**，而不是画一张缺了信息的图。

对应的实现：`render.uncovered()` 判定、`render.require_covered()` 与 `host` 在发图前拒绝。

## 6. 判分规则

### 6.1 逐段判分

判分**分段进行**（设计见 `README.md` §4.2）：段内仍然是严格判据（**全对才算理解**），但**段与段互不连累**。

| 段 | 项 | 规则 |
| --- | --- | --- |
| 一、三 | 单题 | 归一后与基准状态一致 → 正确；否则错误 |
| 一、三 | 基准 | 第一步=**世界的当前状态**（尚无物体被移动）；第三步=**被测者通过操作表现出的世界状态** |
| 一、三 | 单题 | 第三步额外与世界的当前状态再比一次，结果**记进记录**，但**不参与判分** |
| 一、三 | 无效题 | 定指不唯一等，**不计入分母**，并警告出题方 |
| 一、三 | 汇总 | 正确数 / 该段实际问到的题数 |
| 二 | 每个操作 | 按 §5.4 的 **2×2 表**判该条指令；每个操作之后两份状态对拍，不一致记入该段 |
| 二 | 非法操作 | 被测者执行非法操作 → **直接判不理解**（见 §3.3） |

- **第三步以被测者通过操作表现出的世界状态 为准**，因此一个做错的操作**不会**让它后面的问句失去意义：它答的是"按它自己的调用演化出来的世界"，自洽即算答对。
- 第三步同时也与世界的当前状态比对，**只作记录**（记录里逐题标出该状态下的答案与是否答对）。两份状态的差异来源只有一种：第二步出过错；所以这一次比对是诊断信息，不是第二重惩罚。
- **两份状态不一致 ⇒ 第二步已至少有一条指令被判错**（都合法且一致地执行时两份必然同步）。反过来不成立：被测者去执行一条非法操作时，两份状态都不会动，因此没有差异。所以对拍是**定位**用的（第几个操作起、哪些物体不同），不额外扣分。
- **整次测试仍给一个结论**，但它是三段结论的合取（段段理解才算整次测试理解），呈现形式是"第一步 10/10 理解 / 第二步 4/4 理解 / 第三步 5/10 不理解"这样的**分段清单**。

段内用严格判据：P0 的题都是封闭式、答案唯一，错一题就是真的错。

**异常与作废**：被测者在**初始观察**上就崩掉、或回一行不是 JSON 的内容，这类失败**不属于任何一段**，会让整次测试作废（记录里单列 `protocol_errors`）。段内的协议错误（某一步崩了）只算该段出错。

### 6.2 记录里能看到什么

`shrdlu-env` 的文字记录与 `--record` 的 JSON 都按段组织：

| 字段 | 含义 |
| --- | --- |
| `stages.initial` / `stages.operations` / `stages.final` | 每段的 `correct` / `total` / `verdict` / `reasons` / `diverged_at` / `drift` |
| `steps[].stage` | 这一步属于哪一段 |
| `steps[].drift` | 该条指令之后两份状态在哪些物体上不一致 |
| `steps[].truth_expected` / `steps[].matches_truth` | 第三步里，世界的当前状态给出的答案是什么、答对没有（只在两份状态给出不同答案时出现） |
| `final_state` / `second_state` / `final_drift` | 剧本演化的终态 / 被测者的调用演化的终态 / 两者的差异 |
| `protocol_errors` | 让整次测试作废的失败（初始观察失败、无法解析的回报） |

`shrdlu-play` 与 `shrdlu-report` 显示的对照，用的就是 **被测者通过操作表现出的世界状态**，因此对**进程外**的被测者同样可用；被测者自己维护的模型不参与判分。

## 7. 附录：场景与样例

世界模型即 §1–§4 所述：三种 kind（`cube` / `pyramid` / `ball`）、三种位置形态（桌面 / 放在某物体上 / 手中）、三个操作、五种题型。场景规模为 **4–6 个物体**，堆高不超过 2（`worldgen.Spec`）；`ball` 与 `pyramid` 都不能支撑（`SUPPORTING_KINDS = ("cube",)`），这条是考点之一（`e` 是球、`d` 是金字塔）。

### 7.1 初态（5 个物体）

| id | kind | color | size | pos |
| --- | --- | --- | --- | --- |
| `a` | cube | green | small | **on `b`** |
| `b` | cube | red | big | table |
| `c` | cube | blue | big | table |
| `d` | pyramid | blue | big | table |
| `e` | ball | yellow | small | table |

> 沿用原版开场：**小绿块叠在大红块上**。

初始状态（供出题与判分）：

| 命题 | 答案 |
| --- | --- |
| `on(a, b)` | true |
| `on_table(b)` / `on_table(c)` / `on_table(d)` / `on_table(e)` | true |
| `clear(a)` | true |
| `clear(b)` | **false** |
| `clear(c)` / `clear(d)` / `clear(e)` | true |
| `supported(a)` | true |
| `supported(b)` | false |
| `count(cubes)` | 3 |
| `count(cubes on table)` | 2 |
| `count(blue things)` | 2 |

### 7.2 指令序列（4 条，含 1 条非法）

| # | 英文 | 操作 | 判定 |
| --- | --- | --- | --- |
| 1 | Pick up the blue pyramid. | `pick_up(d)` | 合法 |
| 2 | Put the blue pyramid on the blue cube. | `put_on(d, c)` | 合法 |
| 3 | Pick up the red cube. | `pick_up(b)` | **非法**（`b` 不 clear：`a` 压在上面） |
| 4 | Put the yellow ball on the green cube. | `put_on(e, a)` | 合法 |

执行这四条之后的状态：

```
a : on b      （始终没动过）
b : table
c : table
d : on c
e : on a
```
