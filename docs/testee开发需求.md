## 一、契约

### 1.1 主要执行流程

一次测试依次走完三段：**初始观察 → 第一轮问句 → 指令 → 第二轮问句** （结构与判定规则见 `设计协议.md` §5–§6）。操作之前提问，考的是被测者有没有看懂交给它的世界；操作之后提问，考的是它有没有跟上世界的变化；这一层更深，与记忆有关。

被测者的每一个行为都是「收到一条消息、回一条消息」，所以一次测试可以看作几次函数调用：消息类型就是入口，消息字段就是入参，回复就是返回值。

```
observe(state | image)   -> 无返回值
question(text)           -> answer(text)
command(text)            -> action(op, args) | refuse(reason)
```

每个入口要做的事如下（上述写法是简写，线上形态是 `{"type":"answer","text":…}` 这样的一行 JSON，见 §4.1）。括注是验收项编号，共六条 T1–T6。

#### 一、`observe(state | image)`（T1）

入参是初始场景：符号状态或一张图。被测者据此建立自己那份世界认识；后面回答问句、判断操作是否合法，都以它为起点。这个入口没有返回值，不需要回复。

#### 二、第一轮的 `question(text)`（T2、T3）

把 `text` 解析成受约束的问句（五种题型与答句词表见 `设计协议.md` §4），返回一个封闭式的答句：`yes`／`no`、一个属性词、或一个数字（T3）。这一轮问的就是初始观察到的那个状态。问句用自然语言描述对象，被测者把描述对应到自己那份模型里的 `id` 上；操作调用里的对象则一律写成 `id`（第三节）。

#### 三、`command(text)`（T4、T5）

一条指令的落实分两件事：在自己的认识上把它应用一次（测试者看不到这一步），并回一条**形式化的操作调用**；后者是测试者判定这一步操作的依据，格式由测试者给定（`action(op, args)`，见 `设计协议.md` §5.4）。做法是：

把 `text` 解析成要执行的操作（`pick_up`／`put_down`／`put_on`），在自己的认识里找到它指的对象，判断这一步是否合法，然后返回两种值之一：

| 情况 | 返回值 |
| --- | --- |
| 合法 | `action(op, args)`：把这条操作调用交给测试者，例如 `action("put_on", ["a", "b"])` |
| 非法 | `refuse(reason)` |

`op` 与 `args` 一律用 `id`（T5）：`the green cube` 是指称，不是标识，测试者会照着 `args` 执行。指称有歧义时应当拒绝并说明。测试者收到 `action` 后就照那个调用执行；而把这条操作应用到**自己那份认识**上只发生在被测者这一侧，后面的答句才与它发出过的调用一致。

#### 四、第二轮的 `question(text)`（T2、T3）

指令发完之后，测试者会再问一组问句。这一轮问的是**这些操作之后**的世界状态，被测者按操作之后的状态作答，也就是把它收到的那些操作逐条应用到自己维护的认识上得到的状态（这份认识如何维护由实现决定，见 §2.3）。两轮的题目由测试者的题库决定，**可能相同、也可能不同**；答案各按当时的状态给出。

#### 五、每个入口都要有返回值（T6）

除 `observe` 外，每个入口都要回一行带 `type` 的 JSON（字段见 §4.1）。沉默不是拒绝，会被记为没有响应；每条回复有超时上限（`shrdlu.ini` 的 `timeout`，默认 10 秒）。

满足 T1–T6 即可被测试者主持并判分，**不要求导出任何内容**；世界信息只来自最初那一次观察，这一条属于边界（§1.2），不是额外的验收项。

### 1.2 三条边界

上面三个入口各有自己的边界，落在被测者一侧就是三条：

- **世界信息以最初那一次观察为全部来源。** 独立进程运行时也只有这一份；同进程运行时同样只用自己维护的认识，不访问测试者的对象。
- **每条消息只回一条。** `observe` 之外各回一条带 `type` 的 JSON，`action` 之后接下一条（§1.1 第三节）；被测者依据自己的认识确信操作已生效；这份自信与世界的实际状态之差，正是「理解」的度量。
- **指称用 `id`。** 操作参数与答句里的对象一律用 `a`/`b` 这类标识，`the green cube` 是描述而非标识（§1.1 第三节）。

## 二、自由度

> 本节说明契约未加限制的部分。凡未落在 §1.2 那三条边界里的，均属于实现的自由选择。

### 2.1 形态

符号式（持有代码描述、查表作答）、视觉式（基于视觉模型观察）以及其它形态均可。测试者不规定实现方式。

### 2.2 运行方式与语言

| 项 | 可选做法 |
| --- | --- |
| **运行方式** | 独立进程（推荐；`shrdlu-env --testee "CMD"` 启动，`play` / `report` 也接受命令）｜按实现名交给 `shrdlu-play` / `shrdlu-report` 直接运行（便于逐步观看与出报告） |
| **语言** | 任何语言，只要实现该行协议 |

### 2.3 自身认识的维护方式

初始观察之后，被测者对世界的掌握只能来自它自己发出的调用。**维护方式由实现自行决定**：

| 可选做法 | 说明 |
| --- | --- |
| **增量维护** | 每执行一个操作就在自己的模型上应用一次 |
| **由初态回放** | 每次需要时从初态重新应用收到的全部操作 |
| **不建符号状态** | 视觉式实现可以只保留像素或特征；只要回答得出来即可 |

测试者判分只看它发出的调用与给出的回答，两种做法没有区别（见 §3.3）。

## 三、判定

### 3.1 单条指令：2×2 表

（同 `设计协议.md` §3.3。）

| 测试者的指令 | 被测者**执行** | 被测者**拒绝** |
| --- | --- | --- |
| **合法** | 正确 | **不理解**（该做未做） |
| **非法** | **不理解**（做了不该做的） | 正确 |

- 被测者必须**先判断合法性再动作**：非法操作不仅不生效，还会**直接判为不理解**。
- 指称存在歧义时**应当拒绝**（`I do not know which object you mean`）。猜测与拒绝均计错，但拒绝是可以解释的。
- 允许**隐式抓取**：`put_on(x, y)` 中 x 不在手中时，语义为先抓起 x。

### 3.2 单个问句

- 归一后与**基准状态**一致即为正确，否则计错。基准状态在第一轮是**世界的当前状态**（此时没有任何变化），在第二轮是**被测者的调用所演化出的那份状态**（§3.3）。
- **必须表态**：空答、`I don't know`、整句作答、词表之外的词**一律计错**。
- 无效题（例如定指不唯一）**不计入分母**，不属于被测者的过失。自动出题的题目是对着指令之后的状态出的，因此某些题在第一轮**问不了**（此时它会跳过、也不计入分母），第二轮才会出现。

### 3.3 整次测试的判定

**段内严格、段间互不连累**：一段里全对才算这一段理解，但一个操作做错不会让后面的问句失去意义（第三轮的基准是「按它自己的调用演化出来的世界」）。整次测试的结论是三段的合取，按段呈现。完整规则见 `设计协议.md` §6.1。

判分只依据两项：**被测者发出的操作调用**与**它给出的回答**。它自己不交出任何状态，测试者也不读它的模型；因此回放式与增量式实现，只要调用与回答相同，判分结果相同。

## 四、接入

### 4.1 协议

测试者通过 `--testee CMD` 启动被测者，双方以**一行一个 JSON** 在 stdin/stdout 上通信；消息类型、字段与语义的规范文本见 `设计协议.md` §5.5（照着它实现即可）。

对接时只需记住三件事：

- **`observe` 是单向通知**：读取即可，不作回复。
- 除 `observe` 外，每条消息**都必须回复**一条带 `type` 的 JSON。
- **`question` 会出现两轮**，两轮之间夹着 `command`；两轮题目是否相同由测试者的题库决定，不要假设第二轮重复第一轮。

### 4.2 最小骨架

最小实现约十行 Python：仅处理协议，不实现任何理解逻辑。 **该骨架已实测可完整运行一次测试**：判定结果为「不理解」，但协议链路是通的。

```python
import json, sys

for line in sys.stdin:
    message = json.loads(line)
    kind = message.get("type")
    if kind == "observe":
        continue                      # 初始观察：存下 state，或把 image 交给视觉模型
    if kind in ("command", "question"):
        reply = {"type": "refuse", "reason": "not implemented yet"}
    else:
        reply = {"type": "refuse", "reason": "unknown message"}
    sys.stdout.write(json.dumps(reply) + "\n")
    sys.stdout.flush()
```

```bash
python3 -m shrdlu.env.cli.env_main --scenario first-version --testee "python3 my_testee.py"
```

`shrdlu-testee` 自己的默认实现、视觉模型与服务地址也可以写在 `shrdlu.ini` 的 `[shrdlu-testee]` 段里（见 `README-env.md` 的配置一节），这样启动命令只剩实现名。

#### Python 绑定

用 Python 实现时不必自己收发 JSON：接口的完整约定见 `README.md` §6，配套的代码文件是
`shrdlu/testee/api.py`。实现其中的 `Testee` 即可：三个方法各对应一个入口：

```python
from shrdlu.testee.api import Action, Observation, Refuse, Testee

class MyTestee(Testee):
    def observe(self, observation: Observation) -> None:
        self.state = observation.state          # 或 observation.image

    def question(self, text: str):
        return "yes"                            # 或 Refuse("...")

    def command(self, text: str):
        return Action("put_on", ("a", "b"))     # 或 Refuse("...")
```

```bash
# 模块:类：独立进程、逐步观看、出报告都用同一个名字
python3 -m shrdlu.env.cli.env_main  --testee my_testee:MyTestee
python3 -m shrdlu.env.cli.play_main --testee my_testee:MyTestee
python3 -m shrdlu.testee.cli.testee_main --impl my_testee:MyTestee
```

基类负责把消息解码后调用对应的方法、再把返回值编码成回复，因此实现这三个方法即可，
不需要自己解析 JSON。其它语言仍按上面的裸协议骨架实现。

实现可自该骨架逐步替换：建议先答对属性题（`attr`），再处理指令，最后处理关系题。

### 4.3 基类已完成的部分

用 Python 绑定时，下面这些**协议层的事**由基类（`Testee.handle`）与进程循环
（`transport.serve`）代做，实现者不必过问：

| 基类代做的事 | 说明 |
| --- | --- |
| 读写那一行 JSON | 从 stdin 读一行、按 UTF-8 解码；把回复写到 stdout 并按行刷新 |
| 按消息类型派发 | `observe` / `question` / `command` 各自调到同名方法 |
| 一条消息一条回复 | `observe` 没有回复；其余消息的返回值被编码成一行回复 |
| 还没观察就提问或下指令 | 回 `refuse`，不必自己记着"还没看过世界" |
| 遇到不认识的类型 | 回 `refuse` |
| 返回值编码 | `Action` 编成 `action`，`Refuse` 编成 `refuse`，字符串编成 `answer`；返回 `None` 表示不回复（沉默按没有回复计） |
| 自己出问题也不崩 | 收到的不是合法 JSON、或某个方法抛异常时，回一条 `refuse`，然后继续读下一条 |
| 观察载荷的解码 | 符号状态与图片（含 base64 与格式）都装进 `Observation`，交给 `observe` |
| 退出 | stdin 关闭时正常结束 |

需要自己实现的，只有三个方法里**属于理解的那部分**：从观察建立自己的世界认识、解析问句并
作答、解析指令并判断合法性后回操作调用或拒绝。这三件事是**被测能力**，基类不代做，也不该
代做。

本仓库不带"半成品"底座：英文解析、世界模型、合法性判断与状态提交都要自己写。仓库里唯一
现成的实现是 `shrdlu/testee/example.py`（十行的最小示例，只回拒绝），可以作为起点。

其它语言没有现成基类，上表这些事要自己写：照 `设计协议.md` §5 与本章的裸协议骨架实现即可。

## 五、自测

### 5.1 可用工具

下面命令里的常设参数（视觉模型、题型过滤、等待上限等）在 `shrdlu.ini` 里设一次即可，用法见 `README-env.md`。

| 工具 | 用途 |
| --- | --- |
| **`shrdlu-testee --impl example`** | 最小示例；确认协议链路通不通 |
| **`shrdlu-play --testee <NAME>`** | **逐步**运行，每一步并排列出世界的当前状态与「被测者通过操作表现出的世界状态」，不一致处以 `<<<` 标注，是定位分歧点最直接的手段 |
| **`shrdlu-report`** | 将一次测试压缩为一个 HTML 文件（按三段分组），便于回顾与转交 |
| **`shrdlu/scenarios/first-version.json`** | 手写场景，含十道题；另写一份 `.json` 用路径传给测试者即可构造特定场景 |
| **`shrdlu-exam --seed N`** | 生成考卷；更换 seed 即更换场景，可用于回归 |

### 5.2 推荐顺序

先让最小示例把链路打通（判定必然是不理解，但消息能对上），再逐步补齐感知、解析与跟踪；每完成一项，即以 `shrdlu-play` 核对 `<<<` 是否减少，并以分段结论确认自己在**哪一段**失分。

### 5.3 常见错误

| 错误 | 说明 |
| --- | --- |
| **不回复** | 沉默不构成拒绝；拒绝亦须回复 `{"type":"refuse"}`，否则记为「没有响应」 |
| **以拒答规避** | 合法指令拒答即判不理解，问句拒答计错；回避无法使判定通过 |
| **非法却执行** | 直接判为不理解，后果重于答错 |
| **以描述性名称指称对象** | 操作参数必须使用 `id`；`the green cube` 是英文描述，不是对象 `id` |
| **在 `action` 之后等回信** | 测试者照调用执行，接着发下一条；世界是否变化，由被测者自行维护 |
| **指令描述有歧义时凭猜测动作** | 应当拒绝并说明；问句仍须按封闭式词表表态，无效题由测试者排除 |
| **在第二轮问句前丢弃或重置自己维护的状态** | 第三步的基准是「被测者的调用所演化出的状态」；重置或丢弃会使回答与自己维护的状态不一致（§3.3） |
| **把两轮问句当成同一时刻的两次提问** | 两轮之间世界已经变了，且**不会**有任何提示；第一轮的答案不能直接套用（§3.3） |
