# 测试者功能介绍

> **公开**：本文是对外公开的正式介绍的一部分。
>
> **读者**：运行测试的人，以及编写被测者的开发者。
>
> **定位**：整台测试台由 **测试者**（`env`）与 **被测者**（`testee`）两部分组成。测试者是**相对固定**的一半：它持有世界与它的当前状态、下发指令、出题、判分、记录；被测者由开发者自行实现，是可替换的一半。
>
> 全文分五部分：**一、概述**（测试者是什么、由哪些程序组成）｜**二、提供的能力**（世界、观察、操作、判分、出题、记录）｜**三、对外承诺**（保证、不提供的、稳定性）｜**四、边界与限制**（外部依赖与范围之外）｜**五、使用方式**（指向使用手册）。
>
> **本文的落点**：测试者提供什么、承诺什么、不提供什么、哪些是稳定契约、边界在哪里。
>
> 线上格式的规范细节见 `设计协议.md`；如何运行见 `README-env.md`；如何编写被测者见 `testee开发需求.md`；文档分工与公开范围见 `README.md` §7。
>
> 本文描述**已实现并通过测试**的行为；未实现的一律标注 **【未实现】**。

## 一、概述

### 1.1 测试者是什么

**测试者提供一个受限的积木世界与一套封闭式问句；它掌握世界的当前状态，负责提问、要求操作、判分与记录。**

一次测试依次完成**三段，逐段给结论**（问句 → 操作 → 再问一组问句）：操作之前提问，看被测者有没有看懂交给它的世界；操作之后提问，看它有没有跟上世界的变化。一个操作做错不会让后面的问句失去意义；判分只依据测试者自己维护的两份世界状态，因而机械、可复现（规则见 `设计协议.md` §5–§6，理由见 `README.md` §4.2）。

测试者不做推理、规划或学习：求值器是机械的，只由问句语法对状态求值。这正是它区别于「世界模型」之处：测试者的状态是**执行**出来的，不需要推断。

### 1.2 组成部分

| 程序 | 角色 | 归属 |
| --- | --- | --- |
| `shrdlu-env` | 主持人：加载场景、下发指令、出题、判分、记录 | 测试者 |
| `shrdlu-scene` | 只生成初态（对象与位置关系） | 测试者 |
| `shrdlu-exam` | 生成完整考卷（初态 + 指令序列 + 题库）并验证其可玩 | 测试者 |
| `shrdlu-render` | 将场景绘制为图片（SVG 或 PNG） | 观察工具 |
| `shrdlu-play` | 逐步观看一次测试 | 观察工具 |
| `shrdlu-report` | 将一整次测试压缩为一个自包含 HTML | 观察工具 |
| `shrdlu-testee` | 被测方；自带一个最小示例，实现由使用者自己写 | 被测者 |

## 二、提供的能力

| # | 能力 | 小节 | 实现 |
| --- | --- | --- | --- |
| E1 | 世界状态 | §2.1 | `world.py` |
| E2 | 观察视图（符号 / 图像） | §2.2 | `snapshot.py` / `env/render.py` |
| E3 | 操作集 O0 及其合法性判断 | §2.3 | `ops.py` |
| E4 | 初始观察与一问一答的消息 | §2.2 | `env/host.py` / `protocol.py` |
| E5 | 问句求值 | §2.4 | `questions.py` |
| E6 | 出题 | §2.5 | `env/scenario.py` / `env/authoring.py` |
| E7 | 判分（三段逐段） | §2.4 | `env/host.py` / `env/answers.py` |
| E8 | 记录与展示 | §2.6 | `shrdlu-play` / `shrdlu-report` |
| — | 场景生成（可复现） | §2.5 | `env/worldgen.py` |

### 2.1 世界与状态

- **物体**：形状（`kind`）、颜色（`color`）、大小（`size`）三个属性，属性的组合唯一确定一个物体。每个物体另有一个**不透明**的 `id`，不携带属性信息，问答与操作都用它指称对象。
- **形状**三种：`cube`、`pyramid`、`ball`。
- **位置**三种：在桌面上、直接放在另一个物体上、被拿在手中（同一时刻至多一个物体被拿着）。
- **可支撑的只有 `cube`**；金字塔的尖顶与球均不能支撑。
- Level 1 的场景规模为 **4–6 个物体**，堆高不超过 2。

规范形式（状态 JSON 的字段与取值）见 `设计协议.md` §1。

### 2.2 观察

- 测试开始时测试者把初始场景交给被测者：一条 `observe`，带符号状态或一张图；整次测试的世界信息就这一份（`设计协议.md` §5.7）。
- 给哪一种由测试者决定：`--observe state`（默认）或 `image`。
- 图片的信息契约与「在手中」场景的拒绝规则见 `设计协议.md` §5.8。
- 提供 `image` 需要 **Pillow** 以栅格化为 PNG；`state` 与其余功能仍然零依赖。

### 2.3 操作

操作集 O0 共三个：`pick_up`、`put_down`、`put_on`。各操作的前置条件、可支撑性规则与非法操作的处理见 `设计协议.md` §3。

### 2.4 判分

测试者在三种消息处判分：`question` 期望 `answer`，`command` 期望 `action` 或 `refuse`，以及每个操作之后两份状态的对照（`observe` 没有回复）。一次测试按三段逐段判定：问句（对初始状态）→ 操作 → 再问一组问句（对操作之后的状态），**段与段互不连累**，段内仍是「全对才算理解」；整次测试结论是三段的合取，按段呈现，例如「第一步 10/10 理解 / 第二步 4/4 理解 / 第三步 5/10 不理解」。

- 两份世界状态都由测试者维护：一份是 **世界的当前状态**（按指令实际执行），一份是 **被测者通过操作表现出的世界状态**（按被测者发来的调用演化）。被测者不需要回报任何状态，也不需要交出它的模型。
- 自动出题的题目是对着指令之后的状态出的，因此有些题在第一步指不到对象：这类题在第一步跳过、不计入分母，记录里标明是哪一段跳过的。

判据的完整规则（2×2 表、答句词表、无效题、第三步的基准、记录字段）见 `设计协议.md` §5–§6；两轮问句的题目如何分配属于出题设计，协议不作规定。

### 2.5 出题

- 题库有两种来源：**手写场景**（`shrdlu/scenarios/first-version.json`）与**自动出题** （`shrdlu-exam --seed N`；同一 seed 必得同一份考卷）。
- 自动出题对每道题在初态与终态各求值一次，仅将**答案会改变**（或在初态下无法指称）的题计入「必须推演」一类，并对这一类题所占比例设下限。

### 2.6 记录与展示

| 程序 | 用途 |
| --- | --- |
| `shrdlu-play` | 逐步执行一次测试，每步暂停；并排显示世界的当前状态与被测者通过操作表现出的世界状态，不一致处标 `<<<` |
| `shrdlu-report` | 将一整次测试压缩为一个自包含 HTML（内联 SVG，零 JavaScript） |
| `shrdlu-env --record PATH` | 将测试记录写为 JSON |

> 记录按三段组织；字段清单见 `设计协议.md` §6.2，用法与参数见 `README-env.md`。展示用的对照就是判分用的那份对照：两者都读测试者自己维护的两份世界状态，被测者的私有模型在两种场合都不会被读取。

## 三、对外承诺

### 3.1 对被测者的保证

测试者作为平台的承诺，实现被测者时可据此设计。

| 保证 | 含义 |
| --- | --- |
| **测试开始时给一次观察** | 一条 `observe` 带着初始场景交给被测者；整次测试的世界信息就这一份（`设计协议.md` §5.7） |
| **一次测试固定三段，走完为止** | 问句 → 操作 → 再问一组问句；没有提前结束，也不会因为某一段出错而跳过后面的段 |
| **两份世界状态都由测试者维护** | 世界的当前状态与被测者通过操作表现出的世界状态；被测者交来的只有操作调用，测试者自己再应用一遍，用来对拍与第三步判分 |
| **一问一答的消息** | 测试者发一条、被测者回一条；`action` 之后测试者照那个调用执行，这一条消息的来回到此为止 |
| **`id` 是唯一沟通标识** | 指称对象一律使用 `id`；`id` 不携带属性信息 |
| **确定性** | 同一场景与同一种子给出同一份考卷与同一串指令；判分机械、可复现 |
| **判据公开** | 2×2 表、三段划分、答句词表与无效题规则均载于 `设计协议.md` |
| **只依据发来的消息** | 测试者判分的依据是被测者发出的调用与给出的回答；它自己维护的世界模型不参与判分 |
| **超时明确** | 每条回复有超时上限（`shrdlu.ini` 的 `timeout`），超时视为没有回复 |
| **stderr 不阻塞、不丢弃** | 被测者写入 stderr 的内容被持续读取，并在测试结束后由测试者转发 |

**明确不保证的**：模型自身的输出（视觉路径所用本地模型可能不确定）；具体场景内容（除手写场景外，生成场景随种子而变）。

### 3.2 明确不提供的能力

| 不提供 | 说明 |
| --- | --- |
| **对被测者思路的判断** | 只比对回答与世界的当前状态，只在操作层面检查合法性 |
| **推理、规划、学习** | 求值器是机械的：问句语法 → 对状态求值 |
| **动作结果的反馈** | 测试者照调用执行，接着发下一条消息（§3.1） |
| **对被测者内部状态的读取** | 判分只看发来的调用与回答（§3.1）；它如何维护认识由它自行决定 |
| **容器与坐标** | 见 §2.1；位置只有桌面、放在某物体上、在手中三种形态 |

### 3.3 稳定性承诺

测试者相对固定，因此须区分哪些属于**可依赖的契约**、哪些**可能变动**。

| 稳定（可依赖） | 可能变动 |
| --- | --- |
| 一行一个 JSON 的消息形态与消息类型 | 具体场景内容与题库 |
| `observe` / `command` / `question` / `action` / `refuse` / `answer` 的语义 | 场景生成的质量准则与参数 |
| 位置只有三种关系形态 | 渲染风格（等轴测的具体画法） |
| O0 三个操作及其前置条件 | **Level 1 的规模上限**（物体数、堆高）；Level 2 将放宽 |
| 问句五种题型与答句词表 | 题型**可能增加**（现有五种保持兼容） |
| 判分规则（2×2、封闭式比对、无效题不计分母、三段逐段判定） | 三段之外**再加**新段、或某段内部判据的细化 |
| `id` 空间与「`id` 不泄露属性」 | 场景生成器的内部算法 |
| Python 接口（`shrdlu/testee/api.py` 的 `Testee` 三个入口与 `Observation` / `Action` / `Refuse`） | 其它语言的绑定、以及接口之外新增的辅助方法 |
| 记录里的**分段字段**（`stages`、`steps[].stage`、`second_state`） | 记录里**新增**字段（增加不算破坏） |

> **变更原则**：**增加**通常不构成破坏（新增题型、新增操作）；**修改**既有语义须同时修改 `设计协议.md` 并在上表登记。世界模型以 §2.1 为准，扩充它属于「修改」。

## 四、边界与限制

### 4.1 外部依赖与范围之外

- **视觉路径需要外部条件**：Pillow，以及一个可调用的本地模型（默认为 ollama 上的 `gemma4:12b-mlx`）；真调模型的那项测试仅在 `SHRDLU_LIVE_VISION=1` 时执行。
- **图片只表达「在桌面上 / 直接放在谁上面」**：含「在手中」的场景不能出图（§2.2）。
- **位置类与指称类问句不做**：其答句是开放式的，与「答句须可机械比对」冲突（见 `README.md` §6.4）。
